# Architecture Review and Missing Controls  
The provided intranet architecture appears to be a basic multi-tier design (front-end/UI, back-end services, data stores) with minimal mention of security. Crucially, there is no explicit IAM layer or access control in the sketch. We recommend introducing a centralized **Authentication/Authorization service** (e.g. an OAuth2/OpenID Connect Identity Provider) as a first step. For example, the MCP (“Model Context Protocol”) pattern suggests that the server should load the user’s full context – including user ID, roles and permissions – at session start. Every request (either local or HTTP) then presents a bearer token (e.g. JWT) that the server validates. This design ensures each API or chat tool knows the caller’s identity and role before proceeding. In practice, one would add an `/auth/me` or similar endpoint that returns a JSON like `{user_id, name, roles:[…], permissions:[…], tenant_id:…}`. If the current diagram lacks any authentication component, it must be added. In short, the minimal design should be augmented with (1) **user login** (via credentials or SSO) issuing a signed token, and (2) token validation middleware in every service. This enforces that *every* data flow is tied back to a logged-in user identity and role.  

# Key Roles and Access Needs  
Typical enterprise roles must be defined with precision. For example, IBM’s description of RBAC gives analogies that we can adapt: an “HR” role might allow *viewing and editing personnel files, managing benefits, and approving leave* (but no direct access to source code or admin settings); a “Finance” role would allow *purchase orders and budgets* (separate from HR or dev data). Concretely for this project, likely roles include **HR Staff** (HR Manager, Recruiter, etc.), **Engineering Staff** (software developers, QA, DevOps), **IT/Infrastructure Admins**, and possibly **General Employees** or **Managers**. Each role should get the *minimum* permissions needed for its function. For instance:  
- **HR**: can query the employee database, read salary/benefit records, and use HR-specific tools. They should *not* access engineering repositories or system admin functions.  
- **Engineer**: can access code documentation, development tools or project data; perhaps request hardware or software but *not* view other employees’ HR data.  
- **IT Admin**: can manage user accounts, system configs, audit logs, and oversee the entire platform (full privileges).  
- **General Employee/Manager**: can view personal profile, announcements, submit requests (e.g. time off), but not edit others’ profiles or backend settings.  
Defining roles this way follows RBAC principles: “users are assigned to roles, and roles have permissions”. Each role name and its allowed operations should be documented in an **Access Control Policy** so implementers know which tools/endpoints to enable. (Standards bodies consider RBAC *the* best-practice model for such scenarios.)  

# RBAC, ABAC and Best Practices  
Role-Based Access Control (RBAC) is a proven model for enterprises: numerous standards (e.g. NIST SP 800‑53, HIPAA, PCI-DSS) implicitly mandate restricting access by job roles. RBAC’s advantage is simplicity and auditability: administrators can review roles and quickly see which users have which access. Crucially, RBAC *enforces least privilege*: “by restricting users’ access to the resources needed for their roles, RBAC can help defend against malicious insiders”. Therefore, implementers should assign each role only the specific permissions needed and no more (the “Principle of Least Privilege”). For example, a junior developer role might allow code checkout but require a lead’s approval to merge changes, so we wouldn’t grant full change rights in the “Developer” role itself.

While RBAC handles broad categories, consider using Attribute-Based or conditional policies for finer control if needed. ABAC allows access decisions based on user attributes (e.g. department, clearance), resource attributes (e.g. document classification), and context (e.g. time of day, location). For instance, an “HR” user might generally see personnel data, but ABAC rules could restrict access to sensitive records outside business hours or from only certain locations. The trade‑off is complexity: ABAC policies can proliferate and be hard to manage. In practice, a hybrid approach is wise: start with clear RBAC roles for the main buckets (HR, Engineer, Admin), then add attribute checks for special cases (e.g. “HR can view salary *only* if on secure network” or “Engineers can modify dev servers only with multi-factor auth”). The MCP ecosystem specifically *mandates* layering: implement RBAC for basic role groups, and then layer any conditional (attribute-based) checks on top. Whatever the model, the MCP spec also requires certain patterns: every client request must be checked against per-client user consent and token claims (e.g. validate the JWT’s audience matches the MCP server and that the user granted this client permission). Notably, **no action should occur without recording it**: every allowed or denied request must be written to an append-only audit log, ensuring full traceability for later review.  

# Authentication and Session Management  
Each user should authenticate (login) to start a session, after which the system issues a secure token (such as a JWT) representing that identity and its roles. In modern designs, we generally avoid one-off “external tokens” per chat; instead users log in with credentials or SSO, receive a signed access token, and include that on every call. As Auth0 docs advise, generate the token at user login and use it for subsequent requests: “token-based authentication is implemented by generating a token when the user authenticates and then setting that token in the Authorization header of each subsequent request”. The token should have a short lifespan (expiring after, say, minutes to an hour) and be protected by HTTPS to prevent interception. Optionally, use refresh tokens for longer sessions. In any case, validate the token on **every** request. The MCP specification explicitly states that servers “must validate tokens on each request rather than relying on HTTP session state”. In practice, this means no relying on stale cookies alone; every API call (and every chat tool invocation) should re-check the bearer token’s signature, expiration, audience, and scopes. Following best practice, we recommend using industry-standard OAuth2/OIDC flows and JWTs, keeping keys secret and rotating them as needed. As [13] emphasizes, always “give tokens an expiration” and use HTTPS for all token transport. 

# Mapping Roles to Data Flows  
Once roles and tokens are in place, map them onto the system’s data flows and services for least-privilege enforcement. For each service or endpoint in the architecture, identify which roles need access and block everyone else. For example:  
- **HR Database Service**: allow read/write only to HR roles. Any engineer or guest call must be denied. The user’s role (from the JWT) should be checked in the service middleware.  
- **Engineering Tools & Repos**: allow software engineers (and Admins) to read/write code assets. HR roles or interns should get a “403 Forbidden” if they try.  
- **Admin/Configuration APIs**: limit exclusively to Admin role. Changes to user accounts or system settings must log the admin ID and role.  
- **Chat/Agent Tools**: register only the tools relevant to the user’s role. As noted in MCP best practices, “derive the user’s role at connection time, then register only the tools that the role is permitted to see”.  For instance, an HR user’s chat agent would have tools to query personnel info, whereas an engineer’s agent would have tools for code search. This prevents the AI from even knowing about disallowed operations.  

In practical terms, implement a policy filter (or API gateway) that inspects the JWT’s `roles`/`permissions` claim for each call. For any data flow (e.g. user calls REST endpoint, or a tool calls a backend service), the system must check “is the user’s role allowed this action?”. If not, block and audit the attempt. One should also consider network segmentation: put different microservices into separate security zones (for example HR services on an internal network) so that low-privilege clients cannot even reach sensitive endpoints. This layered approach ensures that each component in the architecture enforces only the minimal necessary access. 

# Enforcement Policies and Auditing  
To implement RBAC properly, codify the access rules in a centralized policy framework (or middleware) and rigorously audit its operation. Key controls include: 
- **Policy Definition**: Document each role’s permissions and tie them to the exact APIs or data objects. Store these rules in a policy engine or config (CIS or nginx rules, OPA, etc.). This serves as the authoritative source when enforcing access.  
- **Enforcement Points**: Apply access checks at all boundaries. For example, at the API gateway or service entrypoint, validate the JWT and check role claims before any business logic executes. In MCP terms, layer your authorizer so that no request bypasses the role check.  
- **Audit Logging**: Log every access control decision. As one MCP design note stresses, “`AuditWritten` is not optional. Every path — allowed, denied, blocked — flows through it before terminating”. Each log entry should include user ID/role, timestamp, action, resource, and outcome. This complete log is invaluable for compliance and post-incident review. For example, RBAC aids compliance by providing transparency: regulators can see exactly *who* accessed *what* and *when*.  
- **Least-Privilege Reviews**: Periodically review roles and permissions. Confirm that each user’s active roles are still appropriate (especially after personnel changes) and remove any excess access. Automated tests should attempt forbidden operations (e.g. an engineer trying to call an HR API) to verify that the system correctly denies them.  
- **MCP-Specific Patterns**: Follow mandatory MCP auth patterns: maintain a consent registry mapping each user to allowed clients, validate token audience on every call, and do not blindly forward tokens to downstream services. This guards against token misuse. Also implement a confirmation (two-phase commit) for any high-impact write (so the agent must explicitly confirm actions beyond a certain scope).  

By combining these measures—well-defined roles, strict enforcement code, and thorough logging/auditing—the intranet assistant will follow the principle of least privilege and meet enterprise compliance standards. All sensitive paths are protected by role checks, and any anomaly (e.g. an unexpected role attempt) is logged and blocked. In summary, build RBAC into the architecture by defining roles/permissions, enforcing them in the identity layer and each service, and auditing all decisions. This approach satisfies the original architecture’s goals and adds a robust security posture for HR, engineering, and admin users alike.
